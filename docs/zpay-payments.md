# 通用 HTTP 服务与支付宝支付接入

## 架构与边界

Compose 栈新增 `http` 服务（aiohttp），与 Telegram Bot 分进程运行；共用项目 SQLite 数据卷。HTTP 进程不导入 `bot.py`，不运行 Bot 的崩溃恢复，不调用 Panel，也不通过环境变量接收 Telegram/Panel Token。但数据卷仍包含 Bot 配置，两服务属于同一受信任应用边界，不是安全隔离的多租户平台。

- `services/http_server.py`：通用 HTTP 应用、安全响应头、路由挂载。
- `services/zpay.py`：依据用户提供的 ZPAY 文档实现的签名、下单、查单与响应校验。
- `storage/payments.py`：独立于商品的支付账本、唯一交易约束、支付事件。
- `services/payment_processing.py`：可信服务端查单补偿。
- `bot.py`：订阅商品适配器、人民币下单、自动开通/续费任务。

接口依据是用户提供并于 2026-11-14 核对的 [ZPAY 开发文档](https://7-pay.cn/doc.html)。新订单使用浏览器 POST 到 `https://zpayz.cn/submit.php` 的**页面跳转支付**；服务器不再调用 `mapi.php` 下单。`api.php?act=order` 只用于可信服务端查单，不是 API 下单。没有猜测网关关闭订单、有效期、退款或链上支付接口。

## 当前行为

1. 用户在私聊选择新购或续费套餐，点击支付宝支付。
2. 同一事务保存业务订单、人民币金额（整数分）及套餐内容/套餐多内部组 UUID 快照（旧套餐兼容默认单组），并分配 30 位数字商户支付单号。
3. Bot 返回随机能力链接，用户打开 HTTPS 收银台；GET 不创建网关支付单，避免 Telegram 链接预览触发下单。
4. 用户点击“前往 ZPAY 支付宝收银台”，先向本站 POST 通过来源和能力绑定校验。事务将订单从 `new` 改为 `redirected`，再签发固定目标 `https://zpayz.cn/submit.php` 的表单；浏览器自动 POST 跳转，禁用 JavaScript 时可点击备用提交按钮。本站服务器不发送支付创建请求，也不需要 `clientip` / `device`。同一支付单只签发一次跳转请求，刷新/双击不会自动重发。
5. ZPAY 页面负责显示二维码及完成支付宝支付。表单仅包含文档定义的商户号、支付方式、商户单号、商品名、冻结金额、通知/返回地址、可选渠道及 MD5 签名；商户密钥永不交给浏览器。返回地址固定为 `/payments/zpay/return`，不带查询参数；返回信息先验签、校验身份和金额，再通过服务端查询核对，浏览器跳回本身不作为付款证明。
6. 网关 GET 通知 `/payments/zpay/notify`，服务端验签并核对商户、支付方式、商户单号、交易号、整数分金额与成功状态，事务提交到账记录后返回纯文本 `success`。
7. Bot 每 10 秒调度一次支付任务，先处理已到账的订阅订单，再对待核对支付单进行有界并发补查。任务运行时间/网络延迟可能增加实际交付等待时间，不承诺固定 10 秒完成。
8. 用户可在 Bot 我的订单或收银台点击查询。服务端查单同样校验订单身份和金额，每单最多每 30 秒发起一次；后台选择超过 60 秒未查的记录。

**当前只展示支付宝在线支付。USDT、人工审核的新购入口和 USDT 价格展示已隐藏；旧按钮不能创建这些支付订单。旧订单、人工凭证审核能力和原有数据库字段保留，避免丢失历史记录。新增套餐不再要求 USDT 价格。**

套餐价格全部按 CNY 处理。兼容旧价格文本 `200元`、`¥200.00`、`￥200`、`CNY 200`；拒绝负数、零、科学计数法、三位小数、含糊的多币种文本。新增套餐保存规范化两位小数；历史套餐不会批量重写。套餐修改或删除不改变已经生成的支付订单快照。

## 环境配置

在服务器 `.env` 中配置，不要把真实密钥提交到 Git 或发送到聊天：

```dotenv
ZPAY_PID=你的商户ID
ZPAY_KEY=你的商户密钥
PAYMENT_PUBLIC_URL=https://pay.example.com
ZPAY_CID=
HTTP_PORT=8080
HTTP_TRUSTED_PROXIES=实际反代来源IP/32
```

- `PAYMENT_PUBLIC_URL` 必须是完整 HTTPS origin，不带路径、查询参数或用户名密码。
- `ZPAY_CID` 可空；多个渠道按文档以逗号分隔。
- 三项必需支付参数全空时，通用 HTTP 的健康接口仍可用，支付不可用；部分填写或格式错误时 HTTP 服务拒绝启动，避免假成功。
- 支付配置只从环境读取，不通过 Telegram 回显密钥。
- 保护 `.env`、数据卷和备份的读取权限。含 `$` / `#` 等字符的密钥应按 Compose `.env` 规则使用适当引号。
- 不要随意更换仍有未结订单的商户、密钥、Panel 或内部组；本版没有跨商户自动迁移流程。

配置后，通过现有唯一安装入口 `bootstrap.sh install` 更新并重建服务栈。`docker compose restart` 不会载入修改后的环境变量，需要重建容器。安装脚本等待 `remnashop` 和 `http` 两个服务均为 healthy 才报告成功。

### 先部署、稍后填写配置（不启动）

`bootstrap.sh install --no-start` 会准备仓库、初始化 `.env`、校验 Compose 并构建镜像，但不创建或启动应用容器，也不要求此时填写 `ADMIN_ID` / `BOT_TOKEN`。如果该 Compose 项目已有运行中的容器，则拒绝将操作报告为未启动部署；不会擅自停止旧服务。这仅表示部署准备完成，不代表健康或支付验收通过。

对于管理员已经传入、包含 `.git` 且 origin 与显式 `REPO_URL` 一致的可信源码目录，可以附加 `--local-source`，保留当前代码而不执行 fetch/pull。默认安装仍从配置的仓库更新。示例：

```bash
cd /opt/remnashop-pro
REPO_URL=https://github.com/avsba001/RemnaShop-Pro.git bash bootstrap.sh install --no-start --local-source
# 编辑 .env，完整填写 Bot / Panel / ZPAY 配置后再启动并等待两个服务健康：
REPO_URL=https://github.com/avsba001/RemnaShop-Pro.git bash bootstrap.sh install --local-source
```

不要对不可信目录使用 `--local-source`；origin 检查只校验项目目录身份，不是源码签名验证。仅构建模式不会创建 Compose 网络，可信反代地址应在创建网络后按实际 IP 确定。

## HTTPS 反向代理

默认只发布宿主机 `127.0.0.1:8080`，不直接暴露公网。以下以**宿主机 Nginx** 的现有 HTTPS server 块为例，域名需替换为实际域名，TLS 证书配置沿用现有反代：

```nginx
location /payments/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    # 覆盖客户端自带的头，而非盲目信任它。
    proxy_set_header X-Forwarded-For $remote_addr;
    client_max_body_size 8k;
    proxy_connect_timeout 3s;
    proxy_read_timeout 25s;
    # URL 含回调签名或随机收银台令牌，不能写入常规访问日志。
    access_log off;
}
```

不要对 `/payments/zpay/notify` 添加登录、验证码、浏览器挑战、重定向或缓存；网关应能直接 GET 到该路径。返回的 `success` 不应被代理改写。公网无需暴露 `/healthz`。

`HTTP_TRUSTED_PROXIES` 应填写 **HTTP 容器实际看到的直接代理来源**，而不是公网域名 IP。宿主机 Nginx 经 Docker 端口转发时常为该 Compose 网络的网关，可以检查：

```bash
docker inspect remnashop-http --format '{{range .NetworkSettings.Networks}}{{.Gateway}}{{end}}'
```

以实际网络为准，优先配置单个 IP `/32` 或 IPv6 `/128`，不要填写 `0.0.0.0/0` 或 `::/0`。容器化反代应连入可达网络并填写其实际来源；本示例的 `127.0.0.1` 不适用于另一个容器内部。

跳转支付由浏览器直接请求网关，文档不要求 `clientip`，因此不再依赖 HTTP 容器推导真实公网 IP 才能发起付款。反代仍应覆盖而非盲信客户端传入的转发头；不得伪造用户 IP。

## 支付与交付状态、安全及故障处理

支付账本状态和商品交付状态独立：

| 支付状态 | 含义 |
| --- | --- |
| `new` | 本地支付单已创建，尚未请求网关 |
| `redirected` | 已签发浏览器跳转表单，不代表网关已收单或已付款；不自动重发 |
| `creating` | 旧 API 下单屏障，请求可能正在执行；不重放 |
| `ready` | 收到网关支付信息，等待付款 |
| `unknown` | 下单响应或结果无法确认，保留查单/通知能力 |
| `paid` | 验证通知或可信服务端查询后确认到账；不可退回未支付 |

- `UNIQUE(provider, trade_no)` 防止同一网关交易被用于多个商品订单。
- 重复、并发通知只生成一次 `paid` 事件。回调不做 Panel 或 Telegram 网络请求。
- 网关写请求无自动重试，查询不跟随重定向；查单 URL 含密钥，不记录完整请求或异常文本。
- 收银台随机令牌视为敏感能力链接，不应转发给第三方。页面使用 `Cache-Control: no-store`、`Referrer-Policy: same-origin`、防 iframe、HTML 转义和能力绑定的 POST 校验；GET 不会直接创建支付单。反向代理也必须使用 `Referrer-Policy: same-origin`，不要覆盖为 `no-referrer`：后者会使浏览器表单 POST 携带 `Origin: null`，被严格来源校验拒绝。`same-origin` 保留同源表单来源，但不会向外站泄露收银台令牌；外部付款链接额外使用 `rel="noreferrer noopener"`。
- 机器人查询支付结果使用消息显示，不依赖长耗时请求后的第二次按钮弹窗；尚未发起跳转时提示先前往 ZPAY 收银台。
- `creating/unknown` 页面只显示“查询支付状态（不会重新下单）”，不再误导为可以生成二维码；显示最近查单时间和 30 秒限流反馈。网关 `code != 1` 的查单响应是查询失败，不是“查询成功但未付款”；页面和机器人展示经脱敏的 `msg`。查询不存在不会重置创建屏障。
- 旧 API 订单保留原有诊断和状态，不将已尝试过的商户单号自动改为跳转支付。仅尚未尝试过的 `new` 旧单可以迁移到新模式。旧订单若出现 HTTP 403 等错误，管理员核对后在机器人删除未支付订单，再重新购买；不会自动重发。
- 在线支付单不允许走旧的直接取消/拒绝流程，因为文档没有关闭网关支付单的接口，不能假定本地取消后不会到账。旧回调按钮同样有服务端拦截。
- 未经确认到账，管理员“通过”也不能发放在线支付商品。
- 交付沿用原有 `pending → approved → delivered` 及 `extension_applied / unknown / failed` 保护。只有 pending 且已付款才由任务领取；相同续费用户的交付在单 Bot 进程内串行。
- Panel 写入超时/响应丢失、或处理过程中崩溃时，不自动重新开通或再次 Extend。重启会把已开始的交付标为 `unknown`，由管理员核对。已付款但失败/待核对订单不会自动退款，本次没有实现退款。
- 配置缺失等明确写入前失败保留原有安全人工重试入口；无法证明未写入的失败不得重试。
- **限制**：文档未定义支付过期/关闭/取消，故未猜测自动失效规则。若跳转失败、结果未知或支付一直未完成，同套餐会继续返回原待处理订单，需要管理员先核对并删除未支付订单后才能重新购买。每用户限制最多 10 笔未付款且未被删除的支付记录。
- 仅运行一份 Bot；HTTP 可以独立重启，但数据库仍为 SQLite，当前架构不面向多主 Bot/跨机共享数据库。

运维时同时停止两个数据库写入服务再备份/恢复：

```bash
docker compose -p remnashop stop remnashop http
BACKUP_DIR=/opt/remnashop-backups/你的新目录 ./docker-manage.sh backup
# 恢复需要使用现有 restore 确认流程；不要恢复到仍有写入的卷。
docker compose -p remnashop start remnashop http
```

支付账本也在原 SQLite 内，随数据卷备份。恢复旧备份可能丢失已收到的支付/交付状态；必须先在商户后台和 Panel 核对，不可把恢复数据库当作支付重试手段。

## 管理员删除未支付订单

入口：**管理员主菜单 → 订单审计 → 订单详情 → 删除未支付订单**，二次确认令牌绑定管理员且 5 分钟过期；取消、离开删除操作或使用失效按钮都不会执行删除。

- 仅在线支付、业务状态 `pending`、支付未记账、且未进入交付的订单可删除。已到账、处理中、已交付和不确定的 Panel 写入不允许通过本入口删除。
- 删除是列表层的逻辑删除：保留业务订单、支付账本、金额/商品快照、商户支付单号和审计日志。原收银台返回 HTTP 410，不再签发付款请求。
- 订单从管理员及用户的普通列表隐藏，可在“已删除未支付订单”查看；同套餐后续可创建新的独立订单。
- **本地删除不等于关闭网关订单**。已交给浏览器的签名表单或网关链接可能仍能付款。确认界面必须明确提示风险。
- 与回调在同一 SQLite 写事务锁下串行：到账先发生则拒绝删除；删除先发生而后来通过验签/服务端查单核验到账，则自动恢复订单并正常进入交付，记录 `restore_on_payment` 审计。
- 不会自动删除任何生产订单，也不提供抹除支付证据的物理删除。

## 新增其他商品

本版不是“只接收订阅回调”的专用 Webhook：

1. 通用 HTTP 应用通过 `create_app(..., extra_routes=[...])` 挂载其他模块路由。
2. 商品适配器在**受信任的服务端业务事务**内调用 `insert_intent`，指定 `product_kind`、`business_id`、`owner_id`、整数分金额、明确商品名称和业务快照；同一商品类型/业务单号只能建一条支付记录。
3. 所有商品共用同一个 ZPAY 通知入口和身份/金额/交易唯一性校验，不从回调参数执行用户提供的函数或任意 URL。
4. 新商品的消费者查询自己类型的 paid 记录，用自己的持久化状态机领取并交付；不能只靠进程内队列。当前只实现了 `subscription` 消费者，其他类型会记录到账但**不会自动发货**，需要实现适配器及回归测试。
5. 如果未来增加对外下单 API，必须另行实现调用方认证、商品与订单授权、服务端定价、限流及幂等键。当前刻意没有开放匿名“传金额创建订单”的接口。

## 验证与上线检查

本地离线测试覆盖：签名与人民币转换、冻结价格/商品快照、归属、重复及并发通知、跨订单交易重放、金额/商户/状态篡改、重复参数、收银台 HTML 转义与 POST 校验、真实 IP 信任边界、下单屏障、响应丢失不重发、查单补偿、其他商品路由/账本、付款门禁、自动新购/续费和 Panel 超时不重放。原有契约/订单测试应继续通过。

未用真实商户、未支付真实金额、未启动生产 Bot、未验证真实 Panel 写入。Windows 测试环境为 Python 3.14；生产目标仍为 Docker/Python 3.11。依赖解析/轮子兼容检查不等于 Docker 镜像运行验收。

上线前必须由管理员完成：实际域名和可信反代配置、两个容器健康、HTTPS 通知路径可达、真实小额支付、重复通知只交付一次、漏通知后查单补偿、异常交付人工核对、支付日志和备份权限检查。
